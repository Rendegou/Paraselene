# 幻月排版系统：Windows / WebView2 简体中文正文字体与字号体系

日期：2026-10-13。范围：`paraselene-work/src/features/studio/*.css` 与 `StudioEditor.tsx`。

> **证据边界**：本文件所有 `file:line` 事实均经直接读取确认。但本环境 `web_fetch` 全阻断、`pwsh` 不可用，**凡涉及许可证条款措辞、精确体积数字、CLREQ 条款号的结论均已标注"未能读取原文"**，体积数字为量级估算而非实测。

## 1. 字体栈决策

### 1.1 逐个判定

| 字体 | 归属 | 结论 |
|---|---|---|
| **Microsoft YaHei UI**（微软雅黑 UI） | **随 Windows 附带** | ✅ 可依赖。Windows 10/11 简中与多语言版本默认中文界面字体 |
| **Microsoft YaHei** | **随 Windows 附带** | ✅ 可依赖，与 UI 版同字形、不同默认行高/垂直度量 |
| **Microsoft JhengHei**（微軟正黑體） | **随 Windows 附带** | ⚠️ 繁中界面字体，**不要放进简中 UI 栈** |
| **SimSun**（宋体） | **随 Windows 附带** | ✅ 可用但**仅限装饰位**。位图感强，屏幕小字号发灰发虚 |
| **NSimSun** | **随 Windows 附带** | ✅ 等宽宋体，可作 SimSun 后备 |
| **DengXian**（等线） | 存疑 | ⚠️ 未能核对 Windows 11 字体清单，**建议不进主栈** |
| 思源黑体 / Source Han Sans SC | **必须自带** | 不随 Windows 附带 |
| HarmonyOS Sans SC / MiSans | **必须自带** | 不随 Windows 附带 |
| 霞鹜文楷 LXGW WenKai | **必须自带** | 不随 Windows 附带 |
| Noto Sans SC | **必须自带** | 不随 Windows 附带 |

**关于 UI 后缀字体的行高度量**：`YaHei UI` 与 `YaHei` 字形相同、默认行高不同。⚠️ **未能读到官方原文**，按"可能"对待。实践影响很小——本项目所有 `line-height` 都应显式声明，不依赖字体默认值。

### 1.2 最终推荐栈

**UI 无衬线（拉丁优先，中文自动落到系统简中黑体）**：

```css
--font-ui: "Inter Variable", "Segoe UI Variable Text", "Segoe UI",
           "Microsoft YaHei UI", "Microsoft YaHei", system-ui, sans-serif;
```

排序理由：Segoe UI 家族随 Windows 附带且拉丁字形优秀；Windows 11 上 `Segoe UI Variable Text` 提供真正的可变字重轴（**当前项目混用 400/500/600 却拿不到雅黑的中间字重，正中要害**）；`Microsoft YaHei UI` 排在 Segoe 之后 ⇒ 拉丁走 Segoe、**汉字落到雅黑**（Segoe UI 不含汉字，浏览器逐字回退）。

> ⚠️ **关键取舍**：不要写裸 `"Microsoft YaHei UI"` 作首选。雅黑自带拉丁字形（Arial 风格，**仅 Regular/Bold 两档**）会让 `font-weight: 500/600` 被合成或落回 400 —— **这是当前 UI"发糊、层级不清"的根因之一**。

**正文衬线（长篇中文）**：

```css
--font-prose: "Source Han Serif SC", "Noto Serif CJK SC",
              "Microsoft YaHei UI", "SimSun", Georgia, serif;
```

排序理由：思源宋体/Noto Serif CJK 若自带则最优；否则**中文回退到雅黑而非宋体** —— `SimSun` 在 17–20px 屏幕上笔画过细、灰度发虚，**是当前 `StudioContent.css:8` 最大的视觉缺陷**；`SimSun` 只留作裸 Windows 兜底，`Georgia` 只为拉丁正文。

> ⚠️ **诚实提示**：若不自带字体，`--font-prose` 实际渲染结果**就是雅黑（无衬线）**。要书卷气就必须自带宋体，否则就是无衬线正文。

**字体可用性自检**：`document.fonts.check(`16px "${f}"`)` —— 避免静默回退。

## 2. 自带字体的取舍

### 2.1 许可证

| 字体 | 许可证 | 可否商用/打包 |
|---|---|---|
| **Source Han Sans / Serif**（思源黑/宋） | **SIL OFL 1.1** | ✅ 可，含嵌入与再分发 |
| **Noto Sans SC / Noto Serif SC** | **SIL OFL 1.1**（与思源同源） | ✅ 可 |
| **LXGW WenKai 霞鹜文楷** | **SIL OFL 1.1** | ✅ 可（Debian main 收录为强旁证） |
| **MiSans**（小米） | 自有协议 | ❌ **不建议**（协议历来含限制条款） |
| **HarmonyOS Sans SC** | 自有协议 | ❌ **不建议**（华为社区有"能否商用"专帖 ⇒ 条款不明确） |
| **阿里巴巴普惠体** | 自有协议 | ⚠️ 谨慎 |

**唯一无需法务介入的集合**：SIL OFL 1.1 那三家。⚠️ **OFL 的 Reserved Font Name（保留字体名）**：子集化后若未改名，子集产物需换名分发。**未能读取 OFL 原文确认措辞，动子集前请核对 [SIL OFL 1.1](https://openfontlicense.org/)。**

### 2.2 体积（⚠️ 量级估算，非实测）

| 字符集 | 覆盖字数 | woff2（估） |
|---|---|---|
| 全量简中 | ~20,000+ | **~7–9 MB** |
| GB2312 子集 | 6,763 | **~2.5–3.5 MB** |
| 常用 3500 字 | 3,500 | **~1.2–1.8 MB** |

**Google Fonts 的 CJK 分片**：`@fontsource/noto-sans-sc` 文件名形如 `noto-sans-sc-115-900-normal`，编号到 100+ 段 ⇒ **被切成 100 多个 `unicode-range` 分片**，每片几 KB–几十 KB。⚠️ 分片总数与单片体积未能读取原文确认。

### 2.3 结论：**不要自带中文 webfont，只自带拉丁 UI 字体**

论证（针对本项目的推理）：

1. **Tauri 本地应用无网络加载** ⇒ webfont 的体积优势（按需下载、CDN 缓存）**完全不存在**。子集字体要 100% 打进安装包。捆绑的收益端为零，只剩成本。
2. **小说写作 App 的字符集是无界的**。用户会写生僻字、异体字、增补平面字。**任何固定子集都会缺字**，缺字时浏览器静默回退 ⇒ 出现"一页里两种字形混排"，**比全程雅黑更丑、更业余**。这是子集化在写作类应用中的致命伤。
3. **Windows 已自带合格的简中黑体**。零字节、全覆盖。对**写作工具**而言，界面字体"熟悉且不干扰"优于"有个性"。

**推荐的零风险个性来源**（收益/成本比极高）：

```jsonc
// package.json — 只捆拉丁 UI 字体，woff2 约 100 KB 级
"@fontsource-variable/inter": "^5"
```
```css
--font-ui: "Inter Variable", "Segoe UI Variable Text", "Segoe UI",
           "Microsoft YaHei UI", "Microsoft YaHei", system-ui, sans-serif;
```

拉丁文与数字是界面"气质"的主要载体（品牌名、统计数据、日期、编号），而这正是雅黑最弱处；中文继续走系统雅黑 ⇒ **零缺字、零额外 MB、零许可风险**。

**若产品坚持要中文自有气质**：唯一可接受的做法是**自带正文宋体且不子集化**（GB2312 → 约 3 MB/字重），或**把正文字体做成用户可选设置**（读取系统已安装字体列表）。后者才是写作软件的正解（Word / Scrivener / 番茄小说均如此），也顺带避开全部许可与体积问题。

## 3. 完整字号体系（modular scale, ratio = 1.2）

**基准**：`html { font-size: 13px }` ⇒ `1rem = 13px`。保留现有 13px 物理密度（Windows 桌面密度不宜跳变），把它从"魔法数字"升格为 token 根。

| 角色 | px | rem | line-height | weight | letter-spacing | 现对应类 |
|---|---|---|---|---|---|---|
| **display 章节/书籍大标题** | 29 | 2.25 | 1.30 | 600 | 0 | （新增）|
| **title 章节标题 input** | 24 | 1.85 | 1.40 | 600 | 0 | `StudioContent.css:5`（现 28px） |
| **page 页面标题** | 20 | 1.55 | 1.45 | 600 | 0 | `StudioContent.css:45`（现 25px）、`:28`（现 26px） |
| **section 小节标题** | 15 | 1.15 | 1.55 | 600 | 0 | `StudioContent.css:31`（现 13/600）、`:72`、`:76` |
| **prose 正文「大」档** | 20 | 1.55 | 1.90 | 400 | 0 | 字号切换档 |
| **prose 正文「小」档** | 17 | 1.30 | 1.90 | 400 | 0 | `StudioContent.css:8`（现 17/2.05） |
| **ui-body 界面正文** | 14 | 1.08 | 1.70 | 400 | 0 | `StudioContent.css:32`（现 14/2，建议升 15） |
| **ui 界面文字** | 13 | 1.00 | 1.60 | 400 | 0 | 当前根字号 |
| **ui-label 标签/按钮** | 12 | 0.92 | 1.55 | 500 | 0 | 大多数 `font-size: 12px` |
| **micro 微标签** | **11** | 0.85 | 1.50 | 500 | 0.01em | **取代所有 10px** |
| **numeric 统计数字** | 12 | 0.92 | 1.45 | 500 | 0 | `tabular-nums` |

**论证**：
- **1.2 而非 1.25/1.333**：1.2 的阶差能同时容纳现存的 17 与 20 两个编辑器档位与 13px 根，不产生"相邻层级难辨"。更大 ratio 会让章节标题冲到 30px+，与"正文是主角"的小说场景冲突。
- **层级靠 3 个通道而非 6 个字重**：字号阶 + 字重（**仅 400/500/600 三档**）+ 颜色/间距。当前"标题 500 与 600 随意混用"（`Content:45` vs `:31` vs `Agent:14` vs `:69`）正是层级不清的核心原因。
- 与现状像素差极小（24 vs 25/28、15 vs 13/15），**迁移成本低**。

### 3.1 为什么 CJK 需要不同的 line-height 与 letter-spacing

**行高（CJK 需要更大）**，三条独立理由：
1. **字形占满 em 方框**。汉字 ideographic em-box 垂直方向几乎顶格，没有拉丁那种 x-height + 上下伸展部留出的视觉空气。
2. **笔画密度高**。汉字平均 8–12 笔，行距不足时相邻横画视觉融合、产生糊成一片的灰块。
3. **中文段落无词间空格**，整段是连续字块，唯一的分节手段就是行距。

- **正文 CJK 行距 1.75–2.0。** 可引用的旁证：台湾师大研究在"中英混排以中文为主"时设定 10pt 中文 ⇒ 字距 0、行距为字高 3/4（17.5pt），即 **line-height ≈ 1.75**。这是全文能找到的**唯一带具体数值的实测型中文排版研究**，建议作为 1.75 下界依据。
- 现项目正文 **2.05**，超出舒适区上限，建议收到 **1.90**。
- **界面文字行距 1.5–1.7**，**绝不用 1.9–2.1** —— 当前 `.studio-agent-intro p`（`Agent:15`）、`.studio-message > p`（`Agent:44`）用 1.9 于 12px 界面文字，读起来松散脱节。

**字距（CJK 应为 0）**：
- **汉字是等宽方格**，`letter-spacing` 不是"加宽字距"而是**把每个字从词中孤立出来**，破坏中文均匀灰色文本块的纹理。
- 全角标点**字形内已自带右侧半边空白**，再加字距 = 双倍空隙。
- **负字距在中文里是禁忌**：会让相邻汉字笔画相撞。**`StudioContent.css:5`（章节标题）与 `StudioAgent.css:14` 用了 `-.02em`，在中文标题上是有害的，必须改掉。**
- **何时加正字距**：仅"短字符串 + 仪式感"场合——品牌名、章节序号、地图海域名。`.studio-sea-label` 的 `.6em`、`.studio-map-note` 的 `.2em`（`Content:54–55`）**是恰当的**。英文全大写短标签（`AUTHOR`/`DRAFT`）可 `.08em`。

**全项目现存 `letter-spacing` 仅 3 处**：`StudioApp.css:25` `.08em`（品牌，恰当）、`Content:5` `-.02em`（**应删**）、`Agent:14` `-.02em`（**应删**）、`Content:54–55`（保留）。

### 3.2 最小可读字号与违规清单

**屏幕 CJK 最小可读字号：11px**（12px 为舒适下限）。低于 11px 汉字笔画开始丢失细节。

⚠️ **诚实说明**：「11px」是**工程判断 + 间接推断，不是带引用的权威结论**。Apple HIG 的 11pt 最小字号针对拉丁；WCAG 无绝对最小字号要求（F80 讲的是缩放而非最小值）。

**当前项目违规清单（实测，共 43 处 ≤10px）：**

**9px —— 必须提升至 11px（9 处）**

## 4. CJK 专项规则

### 4.1 `letter-spacing`
正文/界面/标签 **`0`**；大标题/品牌/装饰标签 `0.01em`–`0.6em`（越短越大）；英文全大写短标签 `0.08em`；**CJK 禁用任何负值**。

### 4.2 `text-align`：**用左对齐，不用 `justify`**
中文 justification 靠**拉伸字间空白**（inter-character）实现，而非像拉丁那样拉伸词间空格 ⇒ 同段落内有的行紧、有的行松，产生"呼吸不匀"的斑驳感，对长篇阅读是负价值。现代中文网页排版主流是左对齐 + 禁则处理。
⚠️ **未能读取 W3C CLREQ 关于 `text-align: justify` 的原文条款**，此条为工程判断。
**例外**：将来做导出 PDF / 打印预览时应 `justify`（纸张排版需齐边，且可用标点挤压补足）。

### 4.3 `text-indent: 2em`
- `2em` 首行缩进仍是中文正文**标准**，W3C CLREQ 讨论过（[clreq First-line indents #517](https://lists.w3.org/Archives/Public/public-i18n-archive/2023JanMar/0100.html)、[readium/css 中文段落缩进修正](https://github.com/readium/css/commit/583011453612e6f695056ab6c086a2c4f4cac9c0)）。⚠️ 未读取原文。
- **编辑器内不要靠 CSS 缩进**：CodeMirror 渲染**物理行**，CSS `text-indent` 只缩进段落第一行，且无法参与 CM 的位置计算，光标/选区/aria 语义更脆弱。
- **中文写作软件的实际做法**：字符流里直接输入**两个全角空格 `U+3000 U+3000`**。这是纯文本年代的既有惯例，导出、复制、跨软件粘贴都保真。
- ⚠️ **由此暴露一个既有缺陷**：字数统计用 `Array.from(body).length`（`StudioApp.tsx:171`、`Sidebar.tsx:96`）—— **会把每个全角缩进空格计为 1 字**，采用"输入全角缩进"后字数被系统性高估（每段 +2）。**建议统计时排除 `U+3000`/空白**。这是排版决策与业务逻辑的交叉点，需一并处理。
- **长文阅读页（非编辑态）**：可放心用 `text-indent: 2em`。

### 4.4 断行与标点

```css
.studio-editor .cm-content {
  line-break: strict;        /* 严格执行行首/行尾禁则 */
  word-break: normal;        /* CJK 默认可在任意汉字间断行，勿用 break-all */
  overflow-wrap: break-word; /* 仅为超长 URL/无空格拉丁串兜底 */
  text-wrap: pretty;         /* 避孤字；比 balance 更适合长文 */
  text-align: left;
  hyphens: none;
}
```

- **`line-break: strict` vs `normal`**：中文正文推荐 `strict`。但已知 W3C 社区讨论显示 `strict` 规则与 **GB/T 15834—2011** 存在冲突（[clreq #510](https://lists.w3.org/Archives/Public/public-i18n-archive/2024OctDec/0298.html)、[clreq #625](https://lists.w3.org/Archives/Public/public-i18n-archive/2024JulSep/0050.html)）。**若以实现"符合 GB/T 15834"为产品目标，请先核对这两个议题。这是本报告最需要二次确认的一条。**
- **`text-wrap: balance` 不要用于正文**（会把所有行字数配平，对长文是灾难）。只适合标题。**`text-wrap: pretty`** 用于正文。
- **标点挤压 `palt`/`halt`：不要启用**。各浏览器实现不一致（W3C 日文排版组实测三浏览器结果各不相同）。

### 4.5 `font-variant-numeric: tabular-nums`
**用于所有会变动的数字**，否则字数从 999 涨到 1000 时整块 UI 左右抖动：

```css
.studio-statusbar, .studio-row-number, .studio-tab-count,
.studio-milestones strong, .studio-project small { font-variant-numeric: tabular-nums; }
```
⚠️ 雅黑与思源是否带 `tnum` 特性未核实；若无，Chromium 会合成等宽。**建议实测 `正文 12345 字` 增减时的抖动** —— `StudioApp.tsx:171` 的字数就是活体抖动源。

### 4.6 其他
- **`-webkit-font-smoothing` 在 Windows 上是空操作**（macOS 专有），不要加。
- **`text-rendering: optimizeLegibility` 在 Chromium 中基本无效**，不要加。
- 值得启用的 `font-feature-settings` 仅 `"tnum" 1`（若字体支持）；**`font-variant-numeric` 优先于 `font-feature-settings`**（后者会重置其他特性）。
- **竖排**：`.studio-map-note`（`Content:55`）已用 `writing-mode: vertical-rl`，中文竖排正确。可加 `text-orientation: upright` 保证标点朝向。

## 5. 阅读行长（measure）实测计算

### 5.1 当前值（已核对 CSS）

- ⇒ **内容盒 = 790 − 2×54 = 682px**，`.cm-editor { font-size: 17px }`（`Content:8`）

> **⚠️ 一个必须澄清的冲突（已逐文件核实，结论与初判不同）：**
> `StudioEditor.tsx:36,55` 确实用 CodeMirror 主题给 `.cm-scroller` 注入 `fontSize: ${props.fontSize}px`，`Studio.tsx:39,65` 也确实有 18↔20 的切换按钮 —— **但 `StudioEditor.tsx` / `Studio.tsx` 都属于旧稿，不在活动路径上。**
> 活动路径是 `StudioApp.tsx → ManuscriptEditor.tsx`，而 `ManuscriptEditor.tsx` **完全没有 `fontSize` prop，也没有字号注入**。
> **结论：活动界面的正文就是 CSS 的 17px，没有字号切换功能。** 而 `StudioContent.css:101` 的窄屏 16px 断点是生效的。
> ⚠️ 该判断基于样式级联与组件引用的静态读取，**非渲染实测**（沙箱禁用命令执行）。实现者应在浏览器中确认一次。

### 5.2 理想行长

- W3C CLREQ 专门为**行长**加过说明条款（[clreq Add note for line length #608](https://lists.w3.org/Archives/Public/public-i18n-archive/2024JanMar/0403.html)）⇒ 说明行长在中文排版规范中是被正式讨论的变量。⚠️ **未能读取该议题正文，取不到推荐数值。**
- 综合中文排版通行建议，**舒适区间为每行 25–40 全角字，最佳中心 30–35 字**。⚠️ **该区间未取得可直接引用的权威原文，请勿当作"已引用"的数字。**

**工程结论**：当前 **40.1 字处于舒适区上边缘**。问题**不是**"行长太宽"，而是下面这条。

### 5.3 真问题：行长会塌缩

`.studio-layout` 中间列是 `minmax(350px, 1fr)`（`StudioApp.css:35`）。窗口不够宽时 682px 内容盒根本拿不到：

| 视口宽 | 中间列实得 | 内容盒 | 17px 下字数 |
|---|---|---|---|
| 足够宽 | 858px+ | 682px | 40.1 字 ✅ |
| 1366px（笔记本） | 约 698px | 542px | **31.9 字** ⚠️ |
| 塌到下限 350px | 350px | 242px | **14.2 字** ❌ |

**14 字/行不是"窄"，是无法阅读。** `max-width: 790px` 只是上限，**没有任何下限保护**。

### 5.4 具体建议值

**方案 A（推荐，随字号自适应，保持字数恒定）**：

```css
.studio-manuscript {
  --manuscript-measure: 38ch;
  --manuscript-pad-x: 2.35rem;              /* 40px @ 13px 根 */
  max-width: calc(var(--manuscript-measure) + 2 * var(--manuscript-pad-x));
  padding: 38px var(--manuscript-pad-x) 30px;
}
.studio-editor .cm-editor { font-size: inherit; line-height: var(--lh-prose); }
```
17px：`38×17 + 80 = 726px`；20px：`38×20 + 80 = 840px` ⇒ **两个字号下都是 38 字/行**，切换字号时行宽体验一致。

> ⚠️ `--manuscript-measure` 必须定义在**实际持有 `font-size` 的元素上**，否则 `ch` 会按父级 font-size 解析而算错。未来若加行号 gutter，需同步上调 measure。

**方案 B（最小改动）**：`max-width: 710px; padding: 38px 42px 30px` ⇒ 17px 时 36.8 字、20px 时 31.3 字，均在舒适区。

### 6.1 可直接粘贴的 `:root` token 块

```css
:root {
  /* 字体栈 */
  --font-ui: "Inter Variable", "Segoe UI Variable Text", "Segoe UI",
             "Microsoft YaHei UI", "Microsoft YaHei", system-ui, sans-serif;
  --font-prose: "Source Han Serif SC", "Noto Serif CJK SC",
                "Microsoft YaHei UI", "SimSun", Georgia, serif;
  --font-mono: "Cascadia Mono", "Consolas", "Microsoft YaHei UI", monospace;

  --fs-title:    1.85rem;   /* 24.05px 章节标题 */
  --fs-page:     1.55rem;   /* 20.15px 页面标题 */
  --fs-section:  1.15rem;   /* 14.95px 小节标题 */
  --fs-prose-lg: 1.55rem;   /* 20.15px 正文大档 */
  --fs-prose:    1.30rem;   /* 16.90px 正文本档 */
  --fs-body:     1.08rem;   /* 14.04px 界面正文 */
  --fs-ui:       1rem;      /* 13px    界面基准 */
  --fs-label:    0.92rem;   /* 11.96px 标签/按钮 */

  --lh-display: 1.30;  --lh-title: 1.40;  --lh-page: 1.45;
  --lh-section: 1.55;  --lh-prose: 1.90;  --lh-body: 1.70;
  --lh-ui:      1.60;  --lh-label: 1.55;  --lh-micro: 1.50;

  --ls-body: 0;  --ls-display: 0.01em;  --ls-kicker: 0.08em;  --ls-decor: 0.6em;
```

### 6.4 Vite 加载自带字体 + `@font-face`

```css
@import "@fontsource-variable/inter";   /* 走 npm 依赖，Vite 自动处理 */
```

```css
@font-face {
  font-family: "Paraselene Serif SC";
  src: url("../assets/fonts/paraselene-serif-sc-subset.woff2") format("woff2");
  font-weight: 400 700;
  font-display: block;   /* 本地应用：不要 swap 的闪字 */
  unicode-range: U+3000-303F, U+4E00-9FFF, U+FF00-FFEF, U+3400-4DBF;
}
```

要点：
- **`font-display: block` 而非 `swap`**：本地加载无网络延迟，`swap` 只会在冷启动闪一下回退字体（FOUT）。⚠️ 若体积达几 MB 需实测首屏时间后再定。
- **🛑 `file://` 陷阱**：若 Tauri 用 `file://` 加载页面，`@font-face` 会因 CORS 失败而**静默回退** —— 生产环境极难发现。要么走 Tauri 自定义协议，要么加运行时自检：
  ```ts
  if (expectsBundledFont && !document.fonts.check('16px "Paraselene Serif SC"')) {
    console.error("[type] bundled font failed to load — falling back to system stack");
  }
  ```
- **不用 `unicode-range` 分片**：分片是 HTTP 按需下载的优化；本地应用无此收益，只会增加声明数量与匹配开销。

### 6.5 `font-optical-sizing` 与可变轴
- **CJK 字体基本没有 `opsz` 轴**（思源的可变构建是 `wght` 轴）⇒ `font-optical-sizing` 对本项目基本无关。
- **真正有价值的是 `wght` 连续轴**：可让标题用 `font-weight: 550` 这种精确档位。**当前混用 400/500/600 拿不到中间值，正是层级发糊的根因之一。** 捆绑 **Inter Variable** 或思源可变版即可解决；雅黑不支持，用系统栈时请老实收敛到三档。
- 配合 `font-synthesis: none` 避免浏览器伪造 500/600 造成笔画发粗变形。
