# Agent 开发与验收工作流

更新：2026-10-23。适用于本仓库的人与 Agent。本文维护实施、验证和交接过程；产品目标见[产品范围](../product-scope.md)，代码/数据边界见[架构合同](architecture-contracts.md)，前端规则见[前端规范](frontend-standards.md)，视觉角色见[设计系统](../../DESIGN.md)。

## 文档各管一种事实

- `AGENTS.md`：常驻环境、数据和执行边界，按任务路由阅读。
- `docs/product-scope.md`：用户结果、需求编号、当前优先级与非目标。
- `architecture-contracts.md`：数据含义、技术栈与跨层不变量；ADR 保存决策理由。
- `frontend-standards.md` / `DESIGN.md`：分别维护工程规则和视觉/控件角色；不在技能或任务中复制另一套阈值、颜色和组件标准。
- 任务合同：本次结果、修改范围、适用状态与验收条件；不能凭任务条目放宽上面的合同。
- `docs/progress.md`：唯一当前状态和任务队列；evidence 保存某次运行事实，不自行变成下一轮目标。
- [历史索引](../history/README.md)：归档来源与旧流水。旧“未授权/暂停/待实现”和旧 Agent 所有者不是当前指令。

用户新要求改变产品范围时同步产品文档与受影响任务；合同实质矛盾时列出具体条款和影响。普通实现选择、已授权的合成测试与修正自主处理，不因为技能笼统建议增加确认步骤。

## 按完整用户流程实施

1. **定位当前任务。** 看相关需求和当前队列，确认 HEAD、已有差异与真实接线；保留他人成果。小文案/链接修正按相关文件读取，不通读整个历史库。
2. **写清任务合同。** 中等以上改动使用[模板](task-template.md)的字段，可填在现有任务描述中；跨会话/多批次工作保存为 `docs/tasks/<ID>-<name>.md`。模板是输入清单，不要求为每个小改动新建文件。
3. **固定交互和复用依据。** 找已有组件、页面、状态样例与测试；写出允许差异。按风险列正常、空、加载、失败、忙碌、取消、迟到响应、身份切换及长内容；不适用项说明原因。
4. **实施一个可用切片。** 同时完成接线、错误恢复、焦点/本地化和必要验证。业务协调进现有 controller/service/repository，状态留在所有者；新依赖或框架迁移不作为顺手优化。
5. **验证真实行为。** 先运行受影响检查；切片完成后执行适用全量一次。有新修改、新失败或未消除风险再复跑。测试按用户动作、值/语义、身份和数据不变量断言，避免只查实现类型或 Widget 存在。
6. **复核交付。** 核对需求与失败路径、实际命中、键盘与焦点恢复、旧内容保留和迟到响应。审查不以文件长度或测试总数代替行为；复杂/高风险改动增加独立复核。
7. **更新同一状态入口。** 记录实际命令、退出码、源码/工作树和未测项；对应需求、任务和证据，保留历史结果。实现、验证和发布批准分别写明。

涉及框架/API/CLI 用法或版本兼容时，按 Context7 的 resolve → query 查当前文档，并核对固定 SDK；文档更新不自动授权依赖升级。纯文档整理、业务逻辑审查和从零写检查脚本按实际上下文处理。

若当前任务已明确采用多人/多 Agent 协作，标明各自文件与 Flutter SDK/原生构建的所有者；共享写文件、SDK cache 和同一 native 测试库串行使用。交接读取当前任务状态，不续用历史 agentId/PID。

## 按改动选择验证

**文档、注释、包描述**：运行 `pwsh -NoProfile -File scripts/check-docs.ps1`，检查文档职责、链接、历史快照和差异。只有命令/配置语义或实现变化时才增加对应静态/行为验证，不机械跑整套 Flutter/原生矩阵。

新增现行入口时同步 `check-docs.ps1` 的明确检查范围；历史快照仅核验原字节，不将旧内部链接当现行入口。文档门禁本身修改时运行 `pwsh -NoProfile -File scripts/test-docs.ps1`；统一前端入口也执行其正反例。该工具不自动证明语义、标题锚点或外部网页有效，仍需审阅职责与事实。

**Dart 行为或结构**：运行统一静态检查和受影响真实行为测试；完成切片后运行 `pwsh -NoProfile -File scripts/check-frontend.ps1 -Test`。脚本依赖锁定包和正确的生产/test-support DLL；缺工具/依赖为 NOT_RUN，不能记为 PASS。Rust/FFI 变化还应运行受影响 Rust 与真实桥接检查，不能用 fake 替代。

**UI 几何、主题或交互**：增加适用的常规/窄窗、1×/2× 字号、中英、键盘/焦点、状态/对比度检查，并查看实际渲染；参考入口见 DESIGN。截图生成与 golden 比较分开。需要比较时使用 `scripts/check-frontend.ps1 -Golden` 的固定环境，不自动更新基线，失败必须保留、解释并复核。

**发布候选**：选择 `scripts/check-frontend.ps1 -Test -Golden -WindowsBuild`，核对完整 bundle，再关联实际产物上的原生 IME、DPI/多屏、系统窗口/对话框、读屏和净机/安装证据。根据改动和发布声明补必要矩阵；未经验证的产品承诺不得宣布通过。数据接管、真实模型及发布动作仍遵守各自已获授权的具体范围。

现有 `check-frontend.ps1` 的退出码只约束所选检查；物理项仍是单独报告。本文定义发布完成条件，尚未新增自动发布 profile/CI 或保证系统矩阵可自动执行；这些能力按当前队列实施。

## 工具与环境前提

已测工具链见[架构合同](architecture-contracts.md)。应用、纯文本包、检查工具各自先按锁文件恢复依赖，受控离线缓存缺失时说明缺项。脚本的 SDK/DLL 参数可覆盖机器安装路径；环境限制和产品失败分开，不改源码或降级检查来绕过权限/工具缺失。

文档检查只读明确的文档/源码链接与历史快照；前端检查使用受控合成库。不运行原工程 examples、不读取作者库/凭据、不发真实模型请求作为“检查环境”的手段。

## 证据与交接字段

- 任务/需求 ID、时间、HEAD、工作树是否有差异；若有差异，记录实际源码范围/指纹，不能只写 HEAD。
- 实际命令、工作目录、工具/SDK、DLL/字体等影响结果的版本或 hash，以及退出码。
- 关键断言、通过/失败/跳过数量和过滤范围；证据区分 fake、真实 FFI、widget 渲染、golden 和物理系统。
- 已复现问题、只经源码推断的风险、未测项和恢复/下一动作，分别说明。

`PASS / FAIL / NOT_RUN / SKIPPED` 描述一次检查；`PLANNED / IN_PROGRESS / IMPLEMENTED / VERIFIED / RELEASE_READY` 描述一个明确范围的任务或能力。`VERIFIED` 要附适用范围，不能把“文档通过”升级成“应用通过”。历史 PASS 与新提交不是同一证据。

验证产物先写 `build/<run>/`，避免覆盖旧 evidence；完成后只归档可审阅摘要、必要失败/复核片段和指纹到 `docs/evidence/<task>-<date>/`。当前进度保持精简，旧流水归档并记录来源/hash。归档快照按[清单](../history/snapshot-manifest.json)保持原字节，原文中的路径和链接只作历史上下文，不是新 checkout 的开工依赖。
